# Предложения по новому функционалу AuthorToday

Имея воронку, сравнение периодов, фоновую загрузку и MS SQL, ниже — идеи следующих фич.
Приоритет: польза для автора при анализе прочтений, без раздувания в «платформу».

---

## Высокая польза

### 1. Удаление run из UI ✅

На вкладке «Загрузка»: expander «Удалить загрузку» — выбор `run_id`, превью числа `chapter_reads`, подтверждение.
Удаляются `fetch_runs` + связанные `chapter_reads` (`services/runs.py`, `MssqlReadRepository.delete_run`).

### 2. Календарь покрытия данных

По книге: какие дни есть в БД, где пропуски (логика `check_load_gaps` → таблица/график в Streamlit).
Опционально: «загрузить пропуски» одним действием.

### 3. Автозагрузка по расписанию

Раз в месяц (например, прошлый месяц) без UI: Windows Task Scheduler + CLI.
В UI — статус последних автозагрузок / ошибок.

### 4. Сравнение более чем двух периодов

A / B / C или «этот месяц vs средний за N месяцев».

## Аналитика

### 5. Точки провала воронки ✅

Автоподсветка глав с наибольшим падением % от предыдущей и/или % от базы к предыдущему шагу.
На вкладке «Воронка»: блок «Точки провала», красные треугольники на графике, подсветка строк таблицы.
`analyze/funnel.py` → `find_funnel_drop_points` (топ-3 по каждому критерию).

### 6. Тренд дочитывания ✅

График «глава, % от базы» по месяцам для одной книги.
В UI: выбор книги и главы (по умолчанию последняя), skip «Страница книги» и база как у воронки.
Модуль: `analyze/completion_trend.py`, вкладка «Тренд дочитывания».

### 6a. Нужно грузить и другие метрики (time, avgTime) — частично ✅

Сейчас в БД есть `fetch_runs.value_type`; в UI «Загрузка» и CLI (`--value-type` / `--all-metrics`) можно грузить hit / time / avgTime.
Отчёты пока по умолчанию читают hit. Дальше: селектор метрики в воронке/сравнении/тренде.

Архитектура: [docs/metrics_value_types.md](docs/metrics_value_types.md).

### 7. Несколько книг рядом
Одна метрика (дочитывание / μ) по портфелю книг из `dbo.books`.

### 8. Алерты

Например: «за месяц дочитывание упало больше чем на X%» → сообщение в UI, файл или Telegram.

## Удобство

### 9. Сохранённые пресеты отчётов

Книга + периоды + base-order / skip-book-page в yaml или БД — открытие отчёта в один клик.

### 10. Merge multi-month CSV/JSON

Один файл на весь запрошенный период (сейчас при >1 месяца в `-o`/`--json` попадает только последний chunk + warning).

### 11. Заметки к периоду ✅ (подсветка пока только на тренде)

Таблица `dbo.book_notes` (дата + текст, CRUD на вкладке «Тренд»).
На графике тренда дочитывания заметки в выбранном периоде — красные вертикали/маркеры.
Воронка / сравнение — позже.

### 12. Понятные ошибки при «чужой» / несуществующей книге (fetch) ✅

До поиска Kendo: `fetch/page_errors.py` → `StatsPageError` (`forbidden` / `not_found`).
`load_stats_table` проверяет `page_source`; FetchJob/CLI останавливаются с явным текстом.

**Типичные ответы сайта (текст на странице):**

| Ситуация | Текст на author.today (ориентир) | Смысл |
|----------|----------------------------------|--------|
| Нет прав | «В доступе отказано.» + «У вас недостаточно прав…» | Чужая книга / нет прав автора на отчёт |
| Нет страницы | «404. Страница не найдена» + «Страница устарела, была удалена…» | Неверный `book_id` / книга удалена |

**Как правильно реагировать:**

1. **Дождаться DOM после `driver.get`**, затем **сначала** проверить текст страницы (или стабильные CSS/заголовки ошибки), **потом** искать грид. Не тратить полный timeout на отсутствующую таблицу.
2. **Отдельные исключения** (например `AccessDeniedError` / `PageNotFoundError` или один `StatsPageError` с `reason=forbidden|not_found`), не общий `TimeoutException`.
3. **Сообщения пользователю** (UI баннер + CLI stderr) — явные и короткие:
   - forbidden: «Нет доступа к статистике этой книги (чужая или нет прав). Загружайте только свои произведения.»
   - not_found: «Книга/страница не найдена (404). Проверьте book_id.»
4. **Не писать в БД** за этот шаг (как сейчас при любой ошибке). Не создавать «пустой» `fetch_run`.
5. **Мульти-месяц / несколько метрик:** при forbidden/not_found **сразу остановить** всю job (повтор по следующим месяцам бессмысленен для того же `book_id`).
6. **Детекция по устойчивым фрагментам** (`"В доступе отказано"`, `"404. Страница не найдена"`), не по всему абзацу — вёрстка сайта может чуть меняться.
7. **Fallback:** если ни ошибка, ни грид — оставить текущее «таблица не найдена» (сеть, другая вёрстка, сессия).

**Где править:** `fetch/stats_page.py` (проверка после открытия URL) → узкий helper в `parse/` или `fetch/`; проброс через `FetchJob` / `sync_reads`; отображение уже есть через `status=error` + `progress.error`.

**Тесты:** unit на разбор HTML/текста фикстур (forbidden / 404 / нормальная страница с гридом); без живого Selenium.

**Приоритет:** высокий для UX загрузки; маленький объём работ.

## ИИ (опционально, не в ближайший старт)

### 13. ИИ поверх готовых отчётов

ИИ уместен для **интерпретации уже посчитанных цифр**, не для fetch/Selenium и не вместо `analyze/`.

**Имеет смысл:**

1. **Разбор воронки / сравнения** — кнопка «Объяснить отчёт»: на вход топ падений %, μ/σ, p-value, база, skip «Страница книги»; на выход 3–5 предложений (где отвал, что изменилось). Числа считает код, модель только комментирует JSON отчёта.
2. **Заметки к периоду (§11) → гипотезы** — текст вроде «реклама с 5-го» связать с Δμ и предложить, что проверить дальше (не «доказательство»).
3. **Алерты (§8) человеческим языком** — порог срабатывает по правилам; формулировку «что упало / какая глава / за какой период» делает модель.
4. **«Спроси про книгу»** (позже) — вопрос автора → код считает ответ → ИИ оформляет; без свободного SQL от модели.

**Не предлагать как задачу для ИИ:** парсинг Kendo, 404/доступ (§12), gaps, расписание; предсказание продаж; генерация текста глав; отправка сырого текста книг в облако.

**Предусловия:** сначала §5 (точки провала) и селектор метрик в отчётах — без ИИ уже дают основную пользу. Потом один экран с фиксированным промптом над воронкой/сравнением.

**Где править (когда дойдём):** тонкий `services/ai_explain.py` (или аналог) + кнопка на вкладках Funnel/Compare; ключ API только в `.env`; отчёт в промпт — агрегированные метрики, не сырые `chapter_reads` целиком без нужды.

**Приоритет:** низкий / после стабилизации данных и базовой аналитики.

### 14. Защита от дублирующей загрузки

Сейчас повторный fetch того же периода/метрики **добавляет** новый `fetch_run`; аналитика **суммирует** `metric_value` → завышенные цифры. Нужна проверка **до** Selenium.

**Правило блокировки**

- Вход: `book_id`, `[period_start, period_end]`, набор `value_types`.
- Для **каждой** метрики: есть ли у книги `fetch_runs` с тем же `value_type`, у которых заявленный период **пересекается** с запрошенным:
  - пересечение: `existing.period_start <= request.period_end` AND `existing.period_end >= request.period_start`.
- Если пересечение хотя бы по одной выбранной метрике → **не начинать** загрузку, вернуть ошибку со списком конфликтов (`run_id`, метрика, период run, `fetched_at`).
- Разные метрики за те же даты **не** конфликтуют (hit уже есть → time за тот же месяц можно грузить).

**Поведение**

1. Проверка в сервисном слое **до** создания драйвера / старта `FetchJob` (UI, CLI, `sync_reads_by_period`).
2. Исключение вроде `DuplicateFetchError(AuthorTodayError)` с понятным текстом на русском.
3. UI «Загрузка»: `st.error(...)` без запуска job; CLI — stderr + ненулевой exit.
4. Без «тихой» частичной загрузки: если конфликт по одному месяцу/метрике из мультивыбора — стоп всей операции (проще и безопаснее). Позже опционально: грузить только неконфликтующие пары месяц×метрика.

**На чём считать пересечение**

- **v1:** по `fetch_runs.period_start` / `period_end` + `value_type` (то, что пользователь уже «заказывал»).
- Не по фактическим `chapter_reads.read_date` в первой версии (сложнее; дыры внутри run — тема §2 / gaps).
- Учитывать только run'ы этой книги (`work_id`).

**Не в v1 (явно)**

- Флаг `--force` / «всё равно загрузить» — только если понадобится; иначе сначала удалить run (§1).
- Автозамена старого run новым.
- Блокировка по заметкам / другим таблицам.

**Где править**

| Слой | Что |
|------|-----|
| `storage/mssql_repo.py` | `list_overlapping_runs(book_id, start, end, value_types) → list[...]` |
| `services/fetch.py` (или узкий `services/fetch_guard.py`) | проверка перед `FetchJob.start` / `FetchSession` / sync |
| UI `pages/fetch.py` | показать ошибку до `register_job` |
| CLI `cli.py` / `sync_reads` | тот же guard |
| тесты | unit: пересечение / касание границ / разные метрики / нет MSSQL |

**Сообщение (пример)**

> Загрузка отменена: период 2026-07-01 — 2026-07-31 пересекается с уже загруженным hit (run_id=42, 2026-07-01 — 2026-07-31). Удалите run на вкладке «Загрузка» или выберите другой период/метрику.

**Приоритет:** высокий (качество данных); объём небольшой; логично после или вместе с §12.
